# ByteSize iOS App — Design (M5)

Date: 2026-11-19 · Status: draft for Cory's approval (builder check done; Cory's answers folded in) · Sources: Cory's "ByteSize iOS App — Product & Technical
Specification" (2026-11-19, below "the iOS spec"), `ByteSize.md` §5, backlog "iPhone app (M5)".

## 1. Intent and why

The iPhone app becomes Cory's **primary phone app** for ByteSize (the responsive web app stays usable on phones, but
the decision is that a native app is the main phone experience). It exists for what a browser can't do well:
live barcode scanning, the camera, Apple Health in both directions, and fast native logging. Setup, goals and
administration stay on the web app; the phone is for looking at today and logging fast.

## 2. Goals, non-goals, anti-goals

**Goals**
- Sign in to an existing ByteSize account (password, password reset, passkey, OAuth when the server has them on).
- Five-tab app: Dashboard · Food Log · (+) · Goals · My Foods, with a radial quick-add menu on (+):
  Add Food, Scan Food, Photo, Describe Food.
- Dashboard of rearrangeable widgets: Calendar strip, Today's Overview, Water, Weight, Streak, Badges, Shot tracking.
- Food Log for the selected day with tap-to-edit and swipe Move / Copy / Delete (undo toast).
- Goals tab: read-only targets and goals, weigh-in chart (1W/1M/3M/All), log weight, weight history with deltas.
- My Foods: search/filter custom foods, overrides, recipes and quick meals; view nutrition; quick-log.
- Apple Health: read weight, steps, workouts, external water; write weight, water, calories and macros;
  per-type toggles in the Profile sheet.
- Visual parity with the web app's themes (same tokens, light/dark/system), Dynamic Type.
- Backlog item folded in: a scanned barcode that isn't found offers "Scan the nutrition label" to create the food,
  bound to that barcode so the next scan finds it.
- Plate photos and multi-item Describe ("2 eggs, toast and coffee" → three items), which need new server AI work.

**Non-goals (this round)**
- Offline logging / local database / sync queue (decided: online-only first; built so it can be added — §6.3).
- Account setup, goal/target editing, settings beyond the Profile sheet, admin, integrations, Insights.
- Creating or editing recipes and quick meals (web app).
- Home-screen / lock-screen widgets, Siri / App Intents, push notifications (later round).
- Basket scan, "save remainder for tomorrow", restaurant browsing beyond what search already returns.
- App Store release (installed from Xcode / TestFlight for now).

**Anti-goals**
- Any network call from the phone to anything other than Cory's ByteSize server (no OFF/USDA/AI/Culury SDKs or URLs).
- Health sync that creates duplicates (the same weight or meal written twice, or read back into ByteSize as new).
- A logged-in token kept anywhere but the Keychain.
- Logging a repeat food in more than ~3 taps from the Dashboard.
- Numbers on the phone that disagree with the web app for the same day (the server does all nutrition math).

## 3. Constraints

- SwiftUI, **iOS 17+**, Swift Charts, HealthKit, VisionKit (`DataScannerViewController`) for barcodes,
  PhotosUI / camera for photos. No third-party SDKs that make network calls.
- Built and tested on Cory's **MacBook Pro** (macOS 27, Xcode 27.2, Swift 6.4, iOS 26.3 simulator, XcodeGen installed),
  reached through the n8n "Claude – MacBook Pro Command Runner" workflow. Cory has a paid Apple Developer account.
- TDD, as with the web app: logic test-first.
- The server is self-hosted at Cory's own address, so the server URL is entered on the phone.
- Server already supports `Authorization: Bearer <login token>` (from `POST /api/auth/login` etc.), and has every
  data route the app needs (§6.6). Server changes are listed in §6.7.

## 4. Approaches considered

| | Approach | Trade-off | Decision |
|---|---|---|---|
| 1 | `ios/` folder in the ByteSize repo; logic in a local Swift package (`ByteSizeKit`) tested with `swift test`; thin SwiftUI app target; Xcode project generated by XcodeGen | Fast tests, readable diffs; server + app changes for one feature land in one PR | **Chosen by Cory** |
| 2 | Separate `ByteSize-iOS` repo | Clean separation, but paired server/app changes split across PRs and drift | Rejected |
| 3 | One hand-made Xcode project, no package | Familiar, but every test needs the simulator; noisy `.pbxproj` diffs | Rejected |

Offline: **A (online-only) first, designed so B (cached + queued) can be added later** — chosen by Cory.

## 5. Decided by Cory

- Thin client; setup, goals and admin stay on the web (iOS spec).
- Online-only first; offline later.
- Plate-photo recognition and multi-item Describe are in scope, with the server work they need, in the logging round (I3).
- Weight precedence: a weigh-in already in ByteSize wins; Health only fills days with no ByteSize weigh-in (and never
  brings back a weigh-in deleted in ByteSize).
- Activity from Health: import Health **workouts** as ByteSize workouts (they feed the user's workout-calorie
  setting); steps import as steps; raw all-day active energy is not imported (it would double-count).
- Approach 1 (`ios/` in the ByteSize repo).
- Everything in the iOS spec §2–4 (tabs, radial menu, widgets, swipe actions, read-only Goals with chart and
  history using red ↑ / green ↓ / neutral dash, My Foods quick-log, Health toggles, Profile sheet contents).
- From earlier decisions: targets are ranges; calorie budget bar; unknown nutrients count as 0; GLP-1 shot reminders
  in-app only; every icon has an accessibility label (the iOS version of "hover text").

## 6. Design

### 6.1 Repository layout
```
ios/
  project.yml                 XcodeGen spec (app target, test targets, entitlements, Info.plist keys)
  ByteSize/                   App target: SwiftUI views only, App entry, assets (icon from logo.jpg)
  ByteSizeKit/                Swift package
    Sources/ByteSizeKit/
      API/        APIClient, endpoints, DTOs (Codable), errors
      Auth/       Session (token in Keychain, server URL), sign-in flows
      Models/     Day, LogEntry, Nutrients, Targets, WeighIn, Shot, Badge, Food…
      Features/   @Observable view models (AppState, DashboardModel, FoodLogModel, GoalsModel, MyFoodsModel,
                  AddFoodModel, ScanModel, PhotoModel, DescribeModel, ProfileModel)
      Health/     HealthSync (behind a protocol so tests use a fake store)
      Theme/      Theme tokens generated from frontend/src/themes.ts
    Tests/ByteSizeKitTests/
  ByteSizeUITests/            a few smoke UI tests (sign in against a mock server, tab through)
```
The `.xcodeproj` is generated (`xcodegen generate`) and git-ignored. Bundle id and team id go in `project.yml`.

### 6.2 Networking and auth
- One `APIClient` (actor) with a base URL and a token provider; JSON via `Codable`; dates as the server's
  `YYYY-MM-DD` strings for days. Maps the server's error JSON to a friendly message. `URLProtocol` stub in tests.
- **Sign-in screen**: server address (remembered; collapsed to "Server: bytesize.example.com · Change" after first
  success), email, password, "Forgot password?" (only if the server reports email is set up: sends the 6-digit code
  via `POST /api/auth/forgot`, then `POST /api/auth/reset`), "Sign in with a passkey" and "Sign in with
  <provider>" buttons shown only when the server has them on. A public endpoint (or existing one) tells the app which
  of these are available — see §6.7.
- Token stored in the **Keychain**; a 401 signs the user out to the sign-in screen with "You were signed out".
- **Passkeys**: `ASAuthorizationPlatformPublicKeyCredentialProvider` with relying party = the server's host name,
  using the existing `/api/passkeys/login/options|verify` routes. Requires the server to publish
  `/.well-known/apple-app-site-association` (webcredentials) and the app's Associated Domains entitlement
  `webcredentials:<server host>`.
- **OAuth**: `ASWebAuthenticationSession` with callback scheme `bytesize`. The server's callback redirects to
  `bytesize://oauth?ticket=…` when the flow was started by the app; the app swaps the ticket at
  `POST /api/auth/oauth/finish` as the web page does.
- Sign out: `POST` the existing sign-out route, clear Keychain, clear in-memory state.

### 6.3 State
- `AppState` (@Observable, injected via environment): session, `selectedDate`, current `Day` (entries, totals,
  targets in force, streak — from `GET /api/day/:date`), unit preference and theme from `GET /api/settings/me`.
- Changing `selectedDate` anywhere (calendar strip, Food Log header) reloads the day; Dashboard and Food Log read the
  same `Day`. After any write the app re-fetches the day (server is the source of truth for all math).
- **Offline-ready seam**: all reads go through a `Repository` protocol and all writes through a `Commands` protocol
  with one live implementation over `APIClient`. Offline later adds a caching repository and a queued command
  implementation without touching views. No local DB this round.
- Offline behavior now: an inline banner "Can't reach ByteSize" with Retry; writes fail with a toast and nothing is
  half-saved.

### 6.4 Screens
**Navigation**: custom bottom bar (icons only, VoiceOver labels) with an oversized round (+) raised above the bar.
Top-right profile icon on every primary tab opens the **Profile sheet**: name/email, theme override
(Light/Dark/System + the six web themes), Dynamic Type follows the system (plus an in-app text-size step if the
builder finds it cheap), Apple Health toggles, Sign out, and the note "Account and goals are set up in the
ByteSize web app".

**Radial (+) menu**: tap → background blurs/dims, four round buttons spring out in an arc (Add, Scan, Photo,
Describe), (+) rotates to ×; tap × or backdrop to close. Each opens a sheet:
- *Add Food*: search box focused; Recent · Frequent · My Foods sections, then results from `GET /api/foods/search`
  (shows local groups first, appends the rest). Tap → portion sheet (serving, quantity, fraction chips ¼ ⅓ ½ ¾ 1,
  meal defaulted by time of day) → Log (`POST /api/log`).
- *Scan Food*: VisionKit live scanner (EAN-13/UPC-A/UPC-E/EAN-8), haptic on read → `GET /api/foods/barcode/:code` →
  portion sheet. Not found → "Scan the nutrition label" (camera) → `POST /api/photos/analyze` (mode `label`,
  with the barcode) → prefilled review screen → save as a custom food bound to the barcode
  (`POST /api/my-foods`) → portion sheet. Typed-barcode fallback field.
- *Photo*: camera or library → `POST /api/photos/analyze` (mode `auto`) → barcode result goes to the portion sheet;
  plate/meal result (new server mode `plate`, §6.7 change 5) shows the AI's list of items with portions for
  adjustment before logging them together (flagged AI-estimated). Hidden ("needs an AI service with photos") if the
  server has none.
- *Describe Food*: text field (the keyboard's own dictation mic covers voice; no speech SDK) →
  multi-item estimate (§6.7 change 6) → editable list of items → Log all. Hidden if no AI service.

**Dashboard**: vertical stack of widget cards. Edit mode (Edit button or long-press): drag to reorder, remove (−),
"Add widget" drawer listing hidden ones; Done saves. Layout saved to the server as a new layout page `ios`
(§6.7) so it follows the user across phones; falls back to the default order. Widgets:
- *Calendar strip*: week strip, swipe for weeks, dot on logged days (`GET /api/days/logged`), tap sets `selectedDate`.
- *Today's Overview*: calorie budget bar (range band; "N to go" / "In range" / "N over") and rings for protein,
  fiber, water plus carbs/fat figures, matching the web home card.
- *Water*: +8 oz / +16 oz (or ml in metric) buttons → water log entry; written to Health if on.
- *Weight*: latest weigh-in and change; "Log weight" opens the weight sheet.
- *Streak*: current streak with flame and milestone styling as on the web.
- *Badges*: recently earned / pinned badges (`GET /api/badges`).
- *Shot tracking*: last shot, next due date, suggested next site; "Log shot" → dose, site, time
  (`PUT /api/glp1/shots/:day`). Shown only if the user has GLP-1 tracking on.

**Food Log**: header with date (and the strip's day), entries grouped by meal with per-meal totals.
Tap → edit sheet (serving, quantity, fraction, meal, time) → `PATCH /api/log/:id`. Swipe: leading **Copy**,
trailing **Move** and **Delete**. Move/Copy open a date + meal picker → `POST /api/log/move` (copy flag).
Delete is immediate with a 5-second Undo toast. *(Claude's call)* Undo calls a new server restore route (§6.7
  change 7), so the entry comes back exactly as it was (time, AI flag, no merging).

**Goals**: read-only cards for calorie/macro/water ranges and weight goal, plus active goals from `GET /api/goals`;
banner "Goals and targets are managed in the ByteSize web app." Weigh-in chart (Swift Charts line + area,
1W/1M/3M/All, scale weight points and the trend line the web shows). "Log weight" button →
`PUT /api/weigh-ins/:day`. History list: date, weight, delta vs previous (red ↑ gain, green ↓ loss, — none);
swipe to delete a weigh-in.

**My Foods**: search, filter chips (All · Foods · My edits · Recipes · Quick meals), sort (Recent · Most used · A–Z).
Tap → detail with nutrition facts and servings; "Log to today" (to `selectedDate`, meal defaulted) → portion sheet.
No create/edit except what the scan-label flow needs.

### 6.5 Apple Health
- Off until the user turns a toggle on; each toggle requests only its own types. Toggles:
  Read weight · Read steps & workouts · Read water from other apps · Write weight · Write water ·
  Write calories & macros.
- **Reads** run on app open/foreground (and via `HKObserverQuery` background delivery for weight):
  - weight → `PUT /api/weigh-ins/:day` **only for days with no ByteSize weigh-in** (Cory's rule); a day whose
    weigh-in was deleted in ByteSize is not refilled (the server remembers deleted days, §6.7 change 8);
  - steps → `PUT /api/steps/:day`; workouts → `POST /api/workouts` with the Health workout UUID stored so each is
    imported once; raw active energy is not read;
  - external water → water log entries with the Health sample UUID stored on the server (§6.7 change 8), so a
    reinstall or a second phone never imports it twice.
  Samples whose source is ByteSize itself are ignored, so nothing loops.
- **Writes** *(Claude's call)*: every entry, including ones logged on the web. On each app open the app reconciles the
  **last 7 days** (`GET /api/day/:date`) against what it has written, using `HKMetadataKeySyncIdentifier` =
  `bytesize-<type>-<server id>` with a version: new → write, changed/moved → replace, gone → delete.
  Calories/macros are written per log entry as a food correlation; water and weight as their own samples.
- A "last synced" line and a "Sync now" button in the Profile sheet.

### 6.6 Server routes used (all exist today)
Auth (`/api/auth/*`, passkeys, OAuth, forgot/reset), `GET /api/settings/me`, `GET /api/day/:date`,
`GET /api/days/logged`, `POST/PATCH/DELETE /api/log`, `POST /api/log/move`, `GET /api/foods/recent|frequent|search`,
`GET /api/foods/barcode/:code`, `POST /api/photos/analyze`, `POST /api/ai/estimate`, `GET/POST /api/my-foods`,
`GET /api/targets`, `GET /api/goals`, `GET /api/weight`, `PUT/DELETE /api/weigh-ins/:day`, `GET /api/glp1`,
`PUT /api/glp1/shots/:day`, `GET /api/badges`, `PUT /api/steps/:day`, `GET/PUT /api/layouts/:page`.

### 6.7 Server changes (same repo, test-first, shipped before the app parts that need them)
1. Layout page `ios` in `LAYOUT_PAGES`/`PAGE_WIDGETS` with the iOS widget ids.
2. Public "sign-in options" answer (or extend an existing public route): email reset on?, passkeys on?, OAuth
   provider name if on, server version.
3. `/.well-known/apple-app-site-association` serving `webcredentials` for the app id (from an env var
   `IOS_APP_ID=TEAMID.bundle.id`), plus making passkey origin/rpId checks accept the native app's assertion.
4. OAuth: `POST /api/auth/oauth/start` accepts `client: "ios"`; the callback then redirects to
   `bytesize://oauth?ticket=…` instead of the web page (the "same browser" check adapted for this case).
5. Photo analysis mode `plate`: AI with photos returns a list of items (name, portion, nutrients) — no save.
6. Multi-item AI estimate: text → list of items (the existing single-food `POST /api/ai/estimate` stays for the web).
7. Log delete becomes restorable for a short window (soft delete + `POST /api/log/:id/restore`); purged afterward.
8. External ids: water entries, workouts and weigh-ins can carry a Health sample UUID (unique per user), and the
   server remembers weigh-in days the user deleted so Health doesn't refill them.

### 6.8 Errors
Friendly inline messages from the server's error text; network failures show the banner; AI/photo features
disappear when the server says no AI service; nothing is logged without a final tap by the user.

### 6.9 Testing
- `ByteSizeKit`: unit tests for every model and view model with a stubbed `APIClient` (URLProtocol) and a fake
  HealthKit store — run with `swift test` on the Mac (seconds).
- Server changes: Vitest, as the rest of the backend.
- A few XCUITests against a local stub server: sign in, open each tab, open the (+) menu.
- Manual pass on Cory's iPhone for camera, scanner, Health and passkeys (simulator can't do these).
