# ByteSize M3 — Weight, GLP-1, trends, badges — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Weigh-ins with a trend and goal projection, GLP-1 shot/site/side-effect tracking with an in-app injection-day card, weekly trends, badges and vacation mode.

**Architecture:** Task S adds every new table in one migration (0008). Backends A (weight), B (GLP-1), C (trends, badges, vacation) then run in parallel with no further migrations; frontends D (on A), E (on B), F (on C) follow in parallel. Charts are hand-drawn SVG.

**Tech Stack:** Fastify 5, Drizzle + Postgres 16, zod, Vitest; React 18, Vite 6, Tailwind 4, Testing Library. No new dependencies.

**Spec:** `docs/superpowers/specs/2026-11-16-bytesize-m1-m2-design.md` §13.

## Global Constraints

- Every new table has `user_id`; every query filters by the caller (`requireUser`); every new route and table is covered in `isolation.test.ts`.
- Weights stored in kg; shown/entered in the person's units (lb for imperial, 1 lb = 0.45359237 kg). Days are YYYY-MM-DD in the person's timezone; "today" comes from the server's clock helper (tests pin it).
- Trend: `trend₀ = w₀`; `trend += (w − trend) × (1 − 0.9^gapDays)`. Projection window 28 days, needs ≥ 2 weigh-ins ≥ 7 days apart. Re-plan hint threshold 4.54 kg.
- Sites, in rotation order: abdomen_left, abdomen_right, thigh_left, thigh_right, arm_left, arm_right. Side effects: nausea, low_appetite, fatigue, constipation, diarrhea, heartburn, headache; levels 1–3. Next due = last shot + 7 days; on time = within 1 day of due.
- Badge ids: first_weigh_in, lost_5, lost_10, lost_20, … (every 10 lb), halfway, goal_reached, streak_7, streak_30, streak_100, shots_on_time_4.
- Copy: "Weigh in", "Injection day", "Injection overdue by N days", "Next shot {weekday}", "Log shot", "How are you feeling?", "Not enough weigh-ins yet", "Not losing right now", "Your weight has changed — check your plan", "Vacation mode".
- Reminders are in-app only. No new npm dependencies. Unknown stays unknown (no fake zeros in averages: average over days with food logged only).
- Tests RED→GREEN; stage files explicitly; never commit anything under `.superpowers`.

## Review Focus

1. Another user's weigh-ins, shots, side effects, badges and vacations are never readable, writable or counted.
2. Weigh-ins with gaps (a missed fortnight), a single weigh-in, and a gain all give a sensible trend and projection text — no NaN, no negative "days to goal", no date in the past.
3. Timezone edges: a shot or weigh-in logged late evening lands on the person's local day; "Injection day" flips at local midnight; backdated entries re-order history correctly.
4. Vacation days neither break nor inflate the streak; removing a vacation recomputes it; a badge once earned is never lost or duplicated.
5. Weekly averages ignore days with nothing logged; a week with no data shows as empty, not zeros; dose changes mid-week appear on the right date.

### Task S: Schema for M3

**Files:** modify `backend/src/db/schema.ts`; create migration via `cd backend && npx drizzle-kit generate --name m3` (→ `0008_m3.sql`); `backend/tests/m3-schema.test.ts`.

**Interfaces (produces) — exact tables:**
- `weigh_ins`: id serial pk, user_id (userRef), day date, weight_kg double, note text null, created_at; unique (user_id, day).
- `glp1_settings`: user_id pk (userRef), medication text, dose_mg double, injection_weekday int 0–6, updated_at.
- `glp1_shots`: id, user_id, day date, medication text, dose_mg double, site text, note text null, created_at; unique (user_id, day).
- `side_effects`: id, user_id, day date, effects jsonb `Record<string, 1|2|3>`, note text null; unique (user_id, day).
- `badges`: user_id, badge text, earned_on date, seen boolean default false; pk (user_id, badge).
- `vacations`: id, user_id, from_day date, to_day date.
- `targets` or `user_body`: add `targets_weight_kg double null` on `user_body` (the weight the current targets were set with; set when a plan is selected — Task A wires it).
- Migration also inserts one starting weigh-in per existing `user_body` row: day = current_date, weight_kg = user_body.weight_kg (hand-append the INSERT … SELECT to the generated SQL, `on conflict do nothing`).

**Interfaces (produces):**
- `GET /api/glp1` → `{ settings|null, lastShot|null, nextDue: day|null, status: "none"|"upcoming"|"due"|"overdue", overdueDays: number, suggestedSite, shots: Shot[] (newest first, limit 60), doseHistory: {day, doseMg, medication}[] }`.
